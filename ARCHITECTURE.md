## 1. Цель и границы MVP

**Цель демо:** показать работающую первую версию платформы для Фукуока.

**Входит в MVP:**

- каталог отелей и байков (листинг, фильтры, карточка объекта);
- регистрация и вход;
- личный кабинет (профиль, мои заявки, избранное);
- заявки (лиды) с уведомлением менеджера;
- простая админка (объекты, заявки, пользователи, словари).

**Осознанно НЕ входит в MVP:**

- онлайн-бронирование и календари доступности;
- оплаты и платёжные интеграции;
- CRM и финансовый модуль;
- услуги и пользовательские объявления;
- отзывы и рейтинги;
- Redis, очереди, микросервисы, GraphQL, полнотекстовый поиск (Elasticsearch).

Всё из второго списка добавляется миграциями и новыми модулями, **без переписывания ядра** — см. раздел 2.

## 2. Главный принцип: что фиксируем сразу

Три решения принимаются на старте, потому что их поздняя правка = переписывание системы. Остальное — обычная эволюция.

### 2.1. `Listing` — общая сущность каталога

Отель, байк, будущая услуга и пользовательское объявление — это **один тип сущности** с общими полями (название, slug, описание, статус, локация, цена «от», фото, модерация) и **таблицами-расширениями** под специфику (`HotelDetails`, `BikeDetails`, позже `ServiceDetails`).

Если сделать отдельные таблицы `Hotel` и `Bike`, то поиск, фильтры, фото, модерация, заявки и брони придётся дублировать для каждого нового типа, а «пользовательские объявления» превратятся в отдельную систему.

### 2.2. `ListingUnit` — единица инвентаря

То, что реально бронируется:

- отель → unit = **тип номера**, `quantity` = количество таких номеров;
- байк → unit = **модель**, `quantity` = количество машин в наличии.

В MVP unit нужен просто чтобы показать цены («номера от / байк в сутки»). Но именно он позже становится объектом брони. Добавление этого уровня после запуска = переделка каталога, цен, форм админки и всех заявок.

### 2.3. `Request` ≠ `Booking`

- **Заявка (Request)** — лид. Ничего не блокирует, может быть неполной, обрабатывается менеджером вручную.
- **Бронь (Booking)** — контракт. Блокирует инвентарь, имеет статус оплаты, транзакционные гарантии.

Попытка «дорастить» заявку до брони (добавив ей статусы оплаты и блокировку дат) — самая частая причина переписывания подобных платформ. Заявка останется навсегда: как форма «оставить запрос» и как источник лидов в CRM. Бронь придёт рядом, а не вместо. Связь — поле `Request.bookingId`: менеджер конвертирует заявку в бронь одним действием.

### 2.4. Прочие «дешёвые сейчас, дорогие потом» решения

| Решение | Почему сейчас |
|---|---|
| Деньги — целые числа в минорных единицах + `currency` | float в деньгах = гарантированные расхождения в финмодуле |
| Даты проживания — тип `date`, не `timestamp` | ночь — это календарная дата, а не момент времени; таймзона `Asia/Ho_Chi_Minh` |
| `AuditLog` с первого дня | без истории изменений CRM и разбор спорных броней невозможны |
| Поддержка `Idempotency-Key` в POST-эндпоинтах | тот же механизм потом защищает брони и платёжные вебхуки |
| Даты `dateFrom/dateTo` в контракте поиска | позже включают фильтр доступности без смены публичного API |
| Бизнес-логика в service-слое, не зависящем от фреймворка | защищает сильнее, чем выбор самого фреймворка |

## 3. Технологический стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Frontend | **Next.js 15 (App Router) + TypeScript** | SEO каталога критичен для тревел-продукта; SSR/ISR из коробки |
| UI | **Tailwind CSS + shadcn/ui** | быстрая сборка интерфейса, никакого вендор-лока |
| Backend | **NestJS + TypeScript** | модули = будущие границы (bookings, payments, crm); DI, guards, валидация из коробки |
| БД | **PostgreSQL 16** | транзакции, констрейнты и блокировки нужны для защиты от двойных броней |
| ORM | **Prisma** | типобезопасность, внятные миграции, параметризованные запросы |
| Валидация | **Zod** в общем пакете (`nestjs-zod`) | одна схема на бэкенде и фронтенде |
| Хранилище файлов | **S3-совместимое**: Cloudflare R2 (prod) / MinIO (dev) | картинки не в БД и не в репозитории |
| Почта | Resend (или SES) | письма регистрации, сброса пароля, подтверждения заявки |
| Уведомления | Telegram-бот для менеджера | в этом рынке — самый быстрый канал реакции на лид |
| Мониторинг | Sentry (web + api), pino с request-id | |
| i18n интерфейса | next-intl (ru + en) | дёшево сразу, дорого прикручивать позже |

### Ключевая оговорка о выборе бэкенда

**Важнее фреймворка** то, что бизнес-логика живёт в service-слое, не зависящем от Nest/Next. Тогда смена транспорта — это не переписывание.

Альтернатива, если приоритет — максимальная скорость до демо: монолит на Next.js route handlers с той же слоёной структурой. Но следующий этап (вебхуки платежей, фоновое снятие протухших холдов, воркеры CRM) всё равно потребует отдельного долгоживущего процесса. **Рекомендация — сразу отдельный API на NestJS.**

## 5. Модель данных

### 5.1. Пользователи и доступ

**User**
`id, email (uniq), passwordHash, name, phone, locale, role, status, emailVerifiedAt, createdAt, updatedAt`
`role: USER | PARTNER | MANAGER | ADMIN` · `status: ACTIVE | BLOCKED`

**Session**
`id, userId, tokenHash, userAgent, ip, expiresAt, revokedAt, createdAt`
Опаковый токен; в БД только хэш; мгновенный отзыв.

**PasswordResetToken**
`id, userId, tokenHash, expiresAt, usedAt`

### 5.2. Каталог

**Listing**
`id, type (HOTEL | BIKE), slug (uniq), title, shortDescription, description, status (DRAFT | PENDING | PUBLISHED | ARCHIVED), ownerId?, areaId?, address, lat, lng, priceFromAmount, currency, createdAt, updatedAt, publishedAt`

- `ownerId` (nullable) — сейчас всегда `null` (объекты платформенные). Это точка расширения под партнёров и пользовательские объявления.
- `priceFromAmount` — денормализованная минимальная цена по активным юнитам, пересчитывается при сохранении. Нужна для сортировки и списков без JOIN.

**HotelDetails** (`listingId` PK)
`stars, checkInTime, checkOutTime, distanceToBeachM, hasPool, ...`

**BikeDetails** (`listingId` PK)
`brand, model, engineCc, transmission (AUTOMATIC | MANUAL | SEMI), year, depositAmount, depositCurrency, deliveryIncluded`

**ListingUnit**
`id, listingId, name, description, capacity?, quantity, priceAmount, currency, priceUnit (NIGHT | DAY), sortOrder, isActive`

**Area** — районы Фукуока (Duong Dong, Ong Lang, An Thoi, Bai Sao, Bai Truong…)
`id, slug (uniq), name, sortOrder`
Даёт фильтры и SEO-страницы вида `/hotels/ong-lang`.

**Amenity** — словарь удобств и опций
`id, code (uniq), name, icon, appliesTo (HOTEL | BIKE | ANY), sortOrder`

**ListingAmenity** — связь many-to-many
`(listingId, amenityId)` — составной PK

**MediaAsset**
`id, storageKey (uniq), url, width, height, mime, sizeBytes, blurDataUrl, uploadedById, createdAt`

**ListingImage**
`id, listingId, mediaId, alt, sortOrder, isCover`

### 5.3. Заявки

**Request**
`id, publicCode (uniq), type (HOTEL | BIKE | GENERAL), status (NEW | IN_PROGRESS | CONFIRMED | CANCELLED | COMPLETED), listingId?, listingUnitId?, userId?, contactName, contactPhone, contactEmail?, messenger (TELEGRAM | WHATSAPP | ZALO | NONE), messengerHandle?, dateFrom?, dateTo?, guests?, quantity?, comment?, source, assignedToId?, createdAt, updatedAt`

- `userId` nullable — заявку можно оставить без регистрации; при последующем входе заявка привязывается по совпадению телефона или email.
- Даты, юнит и количество присутствуют **уже в MVP** — именно эти поля позже конвертируются в бронь.
- `bookingId?` — поле появится на этапе бронирования.

**RequestNote** — внутренние комментарии менеджера
`id, requestId, authorId, body, createdAt`

**AuditLog** — универсальный журнал изменений
`id, actorId?, entity, entityId, action, before (jsonb), after (jsonb), ip, createdAt`

**Favorite**
`(userId, listingId)` — составной PK, `createdAt`

### 5.4. Схема связей

```
User ──1:N──> Listing            (owner, nullable — задел под партнёров)
User ──1:N──> Request            (nullable — гостевые заявки)
User ──1:N──> Session
User ──N:M──> Listing            (через Favorite)

Area ──1:N──> Listing

Listing ──1:1──> HotelDetails | BikeDetails
Listing ──1:N──> ListingUnit
Listing ──N:M──> Amenity         (через ListingAmenity)
Listing ──1:N──> ListingImage ──N:1──> MediaAsset
Listing ──1:N──> Request

ListingUnit ──1:N──> Request     (nullable)

Request ──1:N──> RequestNote
Request ──N:1──> User            (assignedTo — менеджер)
```

### 5.5. Индексы MVP

- `Listing`: `(type, status, areaId)`, `(status, priceFromAmount)`, `slug` uniq
- `ListingUnit`: `(listingId, isActive)`
- `Request`: `(status, createdAt)`, `(assignedToId, status)`, `(contactPhone)`, `(userId, createdAt)`
- `Session`: `tokenHash` uniq, `(userId)`, `expiresAt`
- `AuditLog`: `(entity, entityId, createdAt)`

### 5.6. Соглашения по данным

- **Деньги:** целое число в минорных единицах + `currency` (VND, USD). Никаких `float`/`double`.
- **Даты проживания:** тип `date`. Таймзона предметной области — `Asia/Ho_Chi_Minh`.
- **Отметки времени:** `timestamptz`, всегда UTC.
- **Удаление:** мягкое (`status = ARCHIVED`) для объектов; жёсткое — только для медиа и по запросу на удаление персональных данных.

## 6. Роли пользователей

| Роль | Права |
|---|---|
| **Гость** (не авторизован) | просмотр каталога, создание заявки |
| **USER** | + личный кабинет, свои заявки, избранное, редактирование профиля, смена пароля |
| **PARTNER** *(зарезервирована, не активна в MVP)* | свои объекты, заявки по своим объектам |
| **MANAGER** | админка: объекты, заявки, словари, медиа |
| **ADMIN** | всё вышеперечисленное + пользователи, роли, блокировки, аудит |

**Правило реализации:** guard защищает маршрут, **service защищает данные**. Проверка владения делается запросом (`where: { id, userId }`), а не сравнением на уровне контроллера. Это единственная надёжная защита от IDOR при росте числа эндпоинтов.

## 7. API

REST, версионирование в пути: `/api/v1`.

### Аутентификация

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/register` | регистрация |
| POST | `/auth/login` | вход, установка cookie-сессии |
| POST | `/auth/logout` | выход, отзыв сессии |
| GET | `/auth/me` | текущий пользователь |
| POST | `/auth/password/forgot` | запрос сброса пароля |
| POST | `/auth/password/reset` | установка нового пароля по токену |
| POST | `/auth/email/verify` | подтверждение email |

### Каталог (публичный, кэшируемый)

| Метод | Путь |
|---|---|
| GET | `/listings?type=&area=&priceMin=&priceMax=&amenities=&guests=&dateFrom=&dateTo=&sort=&page=&perPage=` |
| GET | `/listings/:slug` |
| GET | `/areas` |
| GET | `/amenities?appliesTo=` |

`dateFrom` / `dateTo` принимаются в контракте **уже сейчас**: в MVP они просто прокидываются в форму заявки, на этапе бронирования включают фильтр по доступности — без смены публичного API и без правки фронтенда.

### Заявки

| Метод | Путь | Доступ |
|---|---|---|
| POST | `/requests` | публично, rate-limit + антибот |
| GET | `/me/requests` | USER |
| GET | `/me/requests/:id` | USER (только свои) |

### Личный кабинет

| Метод | Путь |
|---|---|
| GET / PATCH | `/me` |
| POST | `/me/password` |
| GET | `/me/favorites` |
| POST / DELETE | `/me/favorites/:listingId` |

### Админка

| Метод | Путь |
|---|---|
| GET / POST | `/admin/listings` |
| GET / PATCH / DELETE | `/admin/listings/:id` |
| POST | `/admin/listings/:id/publish` · `/archive` |
| GET / POST / PATCH / DELETE | `/admin/listings/:id/units[/:unitId]` |
| GET / POST / PATCH / DELETE | `/admin/listings/:id/images[/:imageId]` |
| GET | `/admin/requests?status=&assignedTo=&type=&q=` |
| PATCH | `/admin/requests/:id` (статус, ответственный) |
| POST | `/admin/requests/:id/notes` |
| GET / PATCH | `/admin/users[/:id]` (ADMIN) |
| GET / POST / PATCH / DELETE | `/admin/areas`, `/admin/amenities` |
| POST | `/admin/media/presign` · `/admin/media/confirm` |
| GET | `/admin/stats` · `/admin/audit` |
| GET | `/health` |

### Соглашения

- **Списки:** `{ "data": [...], "meta": { "page": 1, "perPage": 20, "total": 137 } }`. `perPage` жёстко ограничен сверху.
- **Ошибки:** `{ "error": { "code": "LISTING_NOT_FOUND", "message": "...", "details": {} } }`. Коды — из общего перечня в `packages/shared`.
- **Пагинация:** offset в MVP; курсорная добавляется как альтернативный параметр без слома контракта.
- **Идемпотентность:** заголовок `Idempotency-Key` поддерживается в `POST /requests` с самого начала — тот же механизм затем используется для броней и платежей.
- **Кэширование:** публичные GET каталога отдаются с `Cache-Control` + ISR на стороне Next.js.

## 8. Аутентификация

**Пароли:** argon2id (не bcrypt), параметры по OWASP.

**Сессии:** опаковый случайный токен в cookie `httpOnly` + `Secure` + `SameSite=Lax`; в БД хранится только хэш токена.

Почему не JWT с refresh-ротацией: для MVP это лишняя сложность с ротацией, отзывом и хранением. Опаковая сессия даёт мгновенный отзыв, прозрачную отладку и легко переезжает в Redis без изменения контракта.

**Домены:** `app.example.com` (web) и `api.example.com` (api) на общем родительском домене — cookie работает как same-site, CORS с `credentials: true` и строгим allowlist origin'ов.

**CSRF:** `SameSite=Lax` + обязательный кастомный заголовок на мутациях + double-submit токен.

**Email-верификация и сброс пароля:** одноразовые токены с ограниченным TTL, в БД — хэш. В демо верификация мягкая (не блокирует вход), включается флагом.

**Заготовлено на будущее (добавляется как новые провайдеры к тому же `Session`, без переделки):**

- Google OAuth;
- вход по телефону / OTP (актуально для вьетнамского рынка, Zalo);
- двухфакторная аутентификация для ADMIN.

## 9. Система заявок

### Поток

```
Карточка объекта
   └─> Форма заявки (даты, гости/количество, контакты, мессенджер, комментарий)
        └─> POST /api/v1/requests
             ├─> валидация (zod) + антибот + rate-limit
             ├─> сохранение Request (publicCode вида PQ-4F7K2)
             ├─> уведомление менеджеру: Telegram + email
             ├─> письмо клиенту с publicCode
             └─> запись в AuditLog
                  └─> заявка видна в /account/requests и в /admin/requests
```

### Статусы и переходы

```
NEW ──> IN_PROGRESS ──> CONFIRMED ──> COMPLETED
 │           │              │
 └───────────┴──────────────┴────────> CANCELLED
```

Переходы выполняются **только через метод сервиса**, который проверяет допустимость перехода и пишет `AuditLog`. Прямая правка статуса запросом к БД запрещена политикой ревью.

### Почему это уже «нулевая CRM»

В `Request` есть ответственный, заметки, история изменений и источник. На следующем этапе поверх надстраиваются `Client` (дедупликация контактов по телефону), `Deal`, `Task`, воронка — **без изменения самой заявки**. Данные из MVP мигрируют backfill-скриптом.

### Антиспам

- rate-limit по IP и по номеру телефона;
- honeypot-поле в форме;
- Cloudflare Turnstile (подключается флагом, в демо можно выключить);
- жёсткие лимиты длины всех текстовых полей.

## 10. Админка

Route-group `(admin)` внутри `apps/web`. Доступ — `MANAGER` и `ADMIN`, проверка и в layout (server-side), и на каждом эндпоинте API.

| Раздел | Содержание |
|---|---|
| **Дашборд** | новые заявки за сутки/неделю, опубликованные объекты, регистрации, последние действия |
| **Объекты** | таблица с фильтрами (тип, статус, район, поиск). Форма с вкладками: *Основное · Детали типа · Юниты и цены · Фото · Публикация* |
| **Заявки** | доска или таблица по статусам; боковая панель: контакты, даты, объект, комментарий, внутренние заметки, ответственный, смена статуса |
| **Пользователи** | список, фильтр по роли, смена роли, блокировка (только ADMIN) |
| **Словари** | районы (Area), удобства и опции (Amenity) |
| **Медиа** | библиотека загруженных изображений, поиск неиспользуемых |
| **Аудит** | read-only лента `AuditLog` с фильтрами по сущности и актору |

**Принцип:** админка не имеет собственной бизнес-логики. Она вызывает те же сервисы, что и публичный API, отличаясь только правами. Это гарантирует, что правила (например, пересчёт `priceFromAmount` или валидация публикации) не разъедутся между интерфейсами.

## 11. Работа с изображениями

### Поток загрузки

```
1. Админ выбирает файл
      └─> POST /admin/media/presign  { filename, mime, sizeBytes }
            └─> сервер валидирует mime и размер, генерирует ключ (UUID),
                возвращает presigned PUT URL

2. Браузер грузит файл НАПРЯМУЮ в R2/MinIO
      (файл не проходит через API — нет нагрузки и лимитов body-parser)

3. POST /admin/media/confirm  { storageKey }
      └─> сервер: HEAD объекта, проверка реальных magic bytes,
          снятие EXIF, вычисление width/height и blurDataUrl (sharp),
          создание MediaAsset
```

### Правила

| Правило | Причина |
|---|---|
| Ключи объектов генерирует **только сервер** (UUID) | path traversal, перезапись чужих файлов |
| Разрешены `jpeg`, `png`, `webp`, `avif`. **SVG запрещён** | SVG — вектор XSS |
| Проверка magic bytes, а не заголовка `Content-Type` | подмена типа на клиенте тривиальна |
| Лимит 8 МБ на файл, лимит числа фото на объект | защита от «раздувания» хранилища |
| EXIF снимается | геометки и данные устройства — утечка PII |
| Бакет без публичного листинга, раздача через CDN | |
| `width`/`height` хранятся в БД | отсутствие layout shift на карточках |
| `blurDataUrl` (крошечный base64) | плавная загрузка без внешних библиотек |

### Ресайз

В MVP — встроенная оптимизация `next/image` с `remotePatterns` на CDN-домен. При росте нагрузки заменяется на imgproxy или Cloudflare Images: **меняется только билдер URL**, модель данных и загрузка не затрагиваются.

## 12. Бронирование — подход на будущее

Не реализуется в MVP. Здесь зафиксирован механизм, чтобы текущая модель ему не мешала.

### Новые сущности

- **Booking** — `id, code, listingId, unitId, userId?, guestContact, dateFrom, dateTo, quantity, status, totalAmount, currency, paymentStatus, holdExpiresAt, requestId?, createdAt`
- **UnitAvailabilityDay** — `unitId, date, bookedCount, blockedCount` с `UNIQUE(unitId, date)`
- **RatePlan / SeasonRate** — сезонные и специальные цены
- **Payment / PaymentEvent** — платежи и журнал вебхуков

### Защита от двойного бронирования

Основной механизм — **посуточные счётчики + одна транзакция**:

1. `BEGIN`
2. `SELECT ... FOR UPDATE` по строке `ListingUnit` (или advisory lock по `unitId`) — сериализует конкурентные попытки на этот юнит;
3. upsert строк `UnitAvailabilityDay` на каждый день диапазона;
4. проверка `bookedCount + blockedCount + qty <= unit.quantity`;
5. создание `Booking` в статусе `HOLD` с `holdExpiresAt` (15 минут);
6. `COMMIT`.

Дополнительные рубежи:

- `CHECK`-констрейнт в БД на уровне строки дня — последний барьер, если логика когда-нибудь ошибётся;
- для уникальных объектов (`quantity = 1`) возможен `EXCLUDE USING gist (unit_id WITH =, daterange WITH &&)` — СУБД физически не даст пересечься диапазонам;
- `Idempotency-Key` обязателен при создании брони — двойной клик и ретрай сети не создают вторую бронь.

### Жизненный цикл

```
HOLD ──(оплата подтверждена)──> CONFIRMED ──> COMPLETED
 │                                  │
 └──(истёк holdExpiresAt)───────────┴──> CANCELLED
        снимается фоновым воркером (BullMQ + Redis)
```

### Деньги и оплаты

- Сумма **всегда** пересчитывается на сервере из `RatePlan`; клиентское значение игнорируется.
- Платёжные провайдеры: Stripe (карты) + локальные VNPay / MoMo / ZaloPay.
- Вебхуки: обязательная проверка подписи + таблица идемпотентности событий по `providerEventId`.
- Финансовый модуль — отдельный ledger (двойная запись), а не поля-суммы внутри `Booking`.

### Что для этого уже готово в MVP

- `ListingUnit` с `quantity`, ценой и единицей цены;
- у `Request` есть `listingUnitId`, `dateFrom`, `dateTo`, `quantity` → конвертация в бронь одним действием;
- деньги в целых, даты как `date`, таймзона зафиксирована;
- `AuditLog` и поддержка `Idempotency-Key`;
- `dateFrom/dateTo` уже в контракте поиска.

Итог: этап бронирования — это **новые таблицы и новый модуль**, а не переделка существующих.

## 13. Security-риски

Отсортировано по приоритету для этого продукта.

| # | Риск | Меры |
|---|---|---|
| 1 | **Broken access control / IDOR** — `/me/requests/:id`, все `/admin/*` | Проверка владения запросом в service-слое (`where: { id, userId }`), а не сравнением после выборки. Guard на роль + явная проверка на данных. Негативные тесты на каждый защищённый эндпоинт |
| 2 | **Утечка PII заявок** (телефоны и почты туристов) — главный актив риска | Контакты видны только `MANAGER`/`ADMIN` и владельцу заявки. PII не попадает в логи, URL и аналитику. Шифрование бэкапов. Политика хранения и удаления |
| 3 | **Атаки на аутентификацию** | argon2id; rate-limit и лок-аут на login/register/reset (по IP и по аккаунту); одинаковые ответы для существующего и несуществующего email (защита от enumeration); в БД — только хэши токенов |
| 4 | **Спам и боты в форме заявки** | Rate-limit по IP и телефону, honeypot, Turnstile, жёсткие лимиты длины полей |
| 5 | **XSS через описания объектов из админки** | Санитизация HTML на сервере (sanitize-html) либо markdown с безопасным рендером; строгий CSP; запрет `dangerouslySetInnerHTML` без санитайзера |
| 6 | **Загрузка файлов** — подмена типа, SVG, size-bomb, path traversal | См. раздел 11: серверные ключи, magic bytes, запрет SVG, лимиты |
| 7 | **CSRF** (аутентификация через cookie) | `SameSite=Lax` + CSRF-токен на мутациях + строгий CORS allowlist с `credentials` |
| 8 | **SQL-инъекции** | Prisma параметризует всё; `$queryRawUnsafe` запрещён политикой code review |
| 9 | **DoS на поиске каталога** | Потолок `perPage`, индексы под все фильтры, `statement_timeout`, ограничение комбинаций фильтров |
| 10 | **Утечка секретов** | Секреты только в серверных env; помнить, что `NEXT_PUBLIC_*` попадают в бандл; `.env` вне репозитория; ротация ключей |
| 11 | **На этапе оплат** | Проверка подписи вебхуков, идемпотентность событий, пересчёт сумм на сервере, отсутствие доверия к клиентским суммам |
| 12 | **Цепочка поставок** | Lockfile в репозитории, Dependabot, `npm audit` в CI, запрет установки пакетов без ревью |
| 13 | **Транспорт и заголовки** | HTTPS-only, HSTS, helmet на API, security headers в Next.js |

## 14. Инфраструктура и окружения

### Разработка

`docker-compose.yml` поднимает PostgreSQL и MinIO. Приложения запускаются локально (`pnpm dev`). Сид наполняет БД районами, удобствами, демо-отелями и байками, тестовыми пользователями всех ролей.

### Демо / прод (рекомендация — самый быстрый путь)

| Компонент | Хостинг |
|---|---|
| `apps/web` | Vercel |
| `apps/api` | Railway или Fly.io (Docker) |
| PostgreSQL | Neon / Supabase / управляемая БД провайдера |
| Файлы | Cloudflare R2 + CDN |
| Почта | Resend |

Альтернатива — один VPS с Docker Compose и Caddy: дешевле и всё в одном месте, но требует ручного администрирования.

### CI

Pull request → lint + typecheck + build + тесты + `prisma migrate diff` (проверка, что миграции применимы). Деплой из `main`.

### Тесты в MVP (минимально достаточный набор)

- unit — сервисы заявок, публикации объектов, расчёта `priceFromAmount`;
- integration — auth-поток и права доступа (позитив + негатив на каждую роль);
- e2e (Playwright) — один сценарий: регистрация → каталог → заявка → её видно в кабинете и в админке.

## 16. Открытые вопросы

Требуют решения до начала реализации.

1. **Языки контента.**
   Интерфейс — next-intl (ru + en) сразу, это дёшево. А тексты объектов: в MVP один язык (ru) с добавлением `ListingTranslation` позже за общим маппером, или сразу мультиязычные объекты?
   *Рекомендация:* один язык в MVP, все чтения объектов идут через единый маппер — тогда добавление переводов не затронет вызывающий код.

2. **Отдельный API (NestJS) или монолит Next.js.**
   *Рекомендация:* отдельный API — ради вебхуков платежей и фоновых воркеров на этапе 2–3.

3. **Хостинг демо.**
   Vercel + Railway + R2 (быстро, дороже) или один VPS с Docker (дешевле, требует администрирования)?

4. **Модель байков.**
   Сдаются как «модель, N штук в наличии» или как отдельные пронумерованные машины с госномерами?
   На архитектуру не влияет (меняется только семантика `ListingUnit.quantity`), но определяет форму админки и будущую логику выдачи конкретной машины.

5. **Объём демо-данных.**
   Сколько отелей и байков должно быть в сиде для показа? Реальные объекты Фукуока или синтетические?
