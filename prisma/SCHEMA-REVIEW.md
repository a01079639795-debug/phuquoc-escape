## 2. Как проверить самостоятельно

Всё запускается **без Docker и без установленного PostgreSQL** — серверы поднимаются из npm-пакетов.

Полный набор, 46 проверок:

```bash
npm run db:verify:all
```

По отдельности:

```bash
npm run db:validate
```

```bash
npm run db:verify
```

```bash
npm run db:verify:race
```

```bash
npm run db:verify:seed
```

Прогон на своей базе (нужен Docker):

```bash
docker compose up -d && npm run db:deploy && npm run db:seed
```

Просмотр данных в браузере:

```bash
npm run db:studio
```

## 3. Результаты проверки

Миграция **фактически применена** к настоящему PostgreSQL, а не только сгенерирована. Всего **46 проверок в трёх наборах — все пройдены**.

**Воспроизводимость миграции:** регенерация из схемы даёт файл, побайтово совпадающий с зафиксированным (`sha256 1cb68495…`). Схема и миграция не разошлись.

**Структура:** 21 таблица, 74 индекса (53 объявлены явно, остальные — первичные ключи и unique-ограничения), 25 внешних ключей.

Движок PostgreSQL 16 в WASM (PGlite).

| Группа | Проверка |
|---|---|

| UNIQUE | Дубль перевода `listing + locale` отклонён |
| UNIQUE | Дубль связи объект+удобство отклонён (составной PK) |

### Набор 2 — гонка при смене обложки, 4 проверки

Настоящий PostgreSQL 18.4 с реальными параллельными соединениями (PGlite однопользовательский, гонку на нём не воспроизвести). Подробности и вывод — в разделе 7.5.

| Проверка |
|---|
| **Наивный сервис (UNSET + SET без блокировки) действительно оставляет ДВЕ обложки** |

## 4. Сущности — 21 модель

### Пользователи и доступ (3)

| Модель | Роль |
|---|---|
| `User` | Аккаунт. Email хранится в нижнем регистре (нормализация в service layer), пароль — argon2id. `phoneNormalized` в E.164 — основа будущей дедупликации клиентов в CRM |
| `Session` | Опаковая серверная сессия. В cookie уходит токен, в БД — только его хэш: дамп базы не даёт войти под пользователем |
| `UserToken` | Одноразовые токены. Одна таблица на подтверждение email и сброс пароля — различаются полем `type` |

### Справочники (4)

| Модель | Роль |
|---|---|
| `Area` + `AreaTranslation` | Районы Фукуока. Дают фильтр каталога и SEO-страницы `/hotels/ong-lang` |
| `Amenity` + `AmenityTranslation` | Удобства отелей и опции байков. `scope` разделяет применимость, `group` — код группы для админки |

### Каталог (9)

| Модель | Роль |
|---|---|
| `Listing` | **Общая сущность каталога.** Всё, что одинаково для любого типа объекта — модерация, локация, фото, заявки, будущие брони — связано с этой таблицей |
| `ListingTranslation` | Переводимые тексты объекта + SEO-переопределения |
| `HotelDetails` | Расширение 1:1, PK = `listingId`. Звёзды, время заезда, расстояния, число номеров |
| `BikeDetails` | Расширение 1:1. Марка, модель, объём двигателя, коробка, залог, доставка |
| `ListingUnit` | **Единица инвентаря.** Отель → тип номера, байк → модель. `quantity` — сколько таких единиц существует |
| `ListingUnitTranslation` | Название и описание юнита |
| `ListingAmenity` | Связь объект↔удобство, составной первичный ключ |
| `MediaAsset` | Файл в объектном хранилище. `width`/`height` известны при загрузке → карточки рендерятся без layout shift |
| `ListingImage` | Привязка изображения к объекту: порядок, обложка, alt |

### Заявки и кабинет (3)

| Модель | Роль |
|---|---|
| `Request` | **Заявка (лид).** Ничего не блокирует. Содержит даты, юнит и количество — именно они конвертируются в бронь на этапе 2 |
| `RequestNote` | Внутренний комментарий менеджера, клиенту не виден. Прототип ленты активности в CRM |
| `Favorite` | Избранное. Составной PK `(userId, listingId)` |

### Служебное (2)

| Модель | Роль |
|---|---|
| `AuditLog` | Универсальный журнал. `entity`/`entityId` — строки, а не связи: журнал переживает удаление объекта и не требует миграции при появлении `Booking`, `Payment`, `Deal` |
| `IdempotencyKey` | Результаты идемпотентных POST. В MVP — только защита формы заявки от двойной отправки; на этапах 2–3 тот же механизм закрывает брони и платёжные вебхуки |

## 5. Карта связей

```
User ──1:N──> Session, UserToken, Favorite            [CASCADE]
User ──1:N──> Listing        (owner, nullable)        [SET NULL]
User ──1:N──> Request        (автор, nullable)        [SET NULL]
User ──1:N──> Request        (ответственный менеджер) [SET NULL]
User ──1:N──> RequestNote    (автор заметки)          [RESTRICT]
User ──1:N──> MediaAsset, AuditLog                    [SET NULL]

Area ──1:N──> AreaTranslation                         [CASCADE]
Area ──1:N──> Listing                                 [RESTRICT]

Amenity ──1:N──> AmenityTranslation                   [CASCADE]

Listing ──1:1──> HotelDetails | BikeDetails           [CASCADE]
Listing ──1:N──> ListingTranslation                   [CASCADE]
Listing ──1:N──> ListingUnit ──1:N──> ListingUnitTranslation   [CASCADE]
Listing ──N:M──> Amenity      (через ListingAmenity)  [CASCADE]
Listing ──1:N──> ListingImage ──N:1──> MediaAsset     [CASCADE / RESTRICT]
Listing ──1:N──> Request                              [SET NULL]
Listing ──N:M──> User         (через Favorite)        [CASCADE]

ListingUnit ──1:N──> Request  (nullable)              [SET NULL]

Request ──1:N──> RequestNote                          [CASCADE]
```

`Listing` имеет две связи на `User`, `Request` — две (автор и ответственный менеджер), поэтому связи именованные (`ListingOwner`, `RequestAuthor`, `RequestAssignee`).

## 6. Правила удаления — это бизнес-решения

Самая содержательная часть для ревью: `onDelete` определяет, что происходит с данными при удалении связанной записи.

| Связь | Правило | Почему именно так |
|---|---|---|
| `Request → Listing` / `ListingUnit` / `User` | **SET NULL** | Заявка не должна исчезать вместе с объектом или аккаунтом — это лид, источник данных для будущей CRM и предмет возможного спора |
| `Listing → Area` | **RESTRICT** | Нельзя удалить район, в котором есть объекты. Скрытие района делается через `isActive`, а не удалением |
| `ListingImage → MediaAsset` | **RESTRICT** | Нельзя удалить файл, пока он где-то используется |
| `RequestNote → User (author)` | **RESTRICT** | Автор комментария не удаляется. Менеджеры блокируются (`status = BLOCKED`), а не стираются |
| `ListingTranslation`, `ListingUnit`, `ListingAmenity`, `ListingImage`, `HotelDetails`, `BikeDetails` → `Listing` | **CASCADE** | Части объекта не имеют смысла без него. При этом сам файл в `MediaAsset` остаётся |
| `Session`, `UserToken`, `Favorite` → `User` | **CASCADE** | |
| `Listing → User (owner)`, `AuditLog → User (actor)`, `MediaAsset → User` | **SET NULL** | Объект и журнал переживают удаление аккаунта |

## 7. Решения, требующие подтверждения

Семь мест, где выбор был неочевиден. Изменить их дешевле сейчас, чем после наполнения базы.

### 7.1. Деньги — `BigInt`, а не `Int`

`Int` кончается на 2 147 483 647 VND (≈ 85 000 $). Для цены за ночь достаточно, для сумм броней и будущего ledger — нет, а менять тип колонки на живых данных означает перезапись таблицы и правку всех типов в коде.

*Цена решения:* `BigInt` не сериализуется в JSON штатно. Форматирование денег обязано идти через маппер service layer — он и так предусмотрен архитектурой.

### 7.2. `timestamptz` вместо `timestamp`

Prisma по умолчанию генерирует `TIMESTAMP(3)` **без** таймзоны. Проставил `@db.Timestamptz(3)` всем 28 полям времени. Без этого прямой SQL, BI-инструменты и будущий вынос API в NestJS могут прочитать время неверно. Даты аренды при этом остались `DATE` — ночь это календарный день, а не момент времени.

### 7.3. `uuid(7)` генерируется Prisma Client, а не базой

У колонок нет `DEFAULT gen_random_uuid()`.

*Плюс:* версия 7 упорядочена по времени — хорошая локальность индекса и естественная сортировка.
*Минус:* вставки чистым SQL обязаны передавать `id` явно. В сиде это учтено.

### 7.4. `slug` канонический, один на все языки

URL будут `/ru/hotels/villa-sunrise` и `/en/hotels/villa-sunrise` — один слаг, разный контент.

Отдельные слаги по языкам добавляются позже полем в `ListingTranslation` с фолбэком в резолвере. **Если для SEO нужны разные слаги сразу — скажи, поправлю до применения миграции.**

### 7.5. Единственность обложки держит service layer, а не БД — с обязательным условием

Prisma не поддерживает частичные unique-индексы (`WHERE isCover = true`), а сырой SQL в миграции ломает `prisma migrate dev` (расхождение схемы и теневой базы). Решение оставлено за service layer.

**Тест на конкурентное обновление показал, что очевидная реализация ломается.** Наивная последовательность «снять флаг со всех → поставить флаг нужному» под параллельной нагрузкой оставляет **две обложки**. Механика гонки в PostgreSQL при уровне изоляции READ COMMITTED:

```
T1: UPDATE … SET isCover=false WHERE listingId=X AND isCover=true   → блокирует строку A
T2: UPDATE … SET isCover=false WHERE listingId=X AND isCover=true   → ждёт на строке A
T1: UPDATE … SET isCover=true  WHERE id=B
T1: COMMIT
T2: разблокирован. Перечитывает строку A — она уже isCover=false и под условие
    не подходит. Строку B он не видит: на момент старта его UPDATE она была false.
    В итоге T2 не снимает ничего.
T2: UPDATE … SET isCover=true  WHERE id=C
T2: COMMIT
                                                    → обложки B и C. Инвариант нарушен.
```

**Обязательный рецепт:** транзакция смены обложки начинается с блокировки родительской строки.

```sql
BEGIN;
SELECT id FROM "Listing" WHERE id = $1 FOR UPDATE;          -- сериализует смену обложки
UPDATE "ListingImage" SET "isCover"=false WHERE "listingId"=$1 AND "isCover"=true;
UPDATE "ListingImage" SET "isCover"=true  WHERE id=$2;
COMMIT;
```

Проверено: с блокировкой два параллельных запроса дают одну обложку, десять одновременных — тоже одну, побеждает последняя завершившаяся транзакция. Тест воспроизводит обе ситуации на настоящем PostgreSQL и **зафиксирован в репозитории** (`npm run db:verify:race`), чтобы регрессия в service layer была поймана.

Тот же приём (`SELECT … FOR UPDATE` по родителю) — основа защиты от двойного бронирования на этапе 2. Механизм отрабатывается заранее на безопасном поле.

### 7.6. `ListingImage.alt` — единственный переводимый текст вне translation-таблицы

Пятая таблица переводов ради alt-текста показалась несоразмерной. Заполняется на языке контента.

### 7.7. `Amenity.group` — строковый код, а не отдельная таблица

Группы удобств («internet», «food», «equipment») нужны только для группировки в админке. Подписи живут в словарях интерфейса.

## 9. Чего в схеме сознательно нет

Особенности реализации:

- контент **только на RU** — как договорились; добавление EN и VI является вставкой строк в `*Translation`;
- `priceFromAmount` считается как минимум по активным юнитам — тем же правилом, которое затем реализует service layer;
- пароль всех демо-аккаунтов `demo1234`, хэш настоящий argon2id — аккаунты заработают сразу, как появится авторизация;
- изображения — стабильные плейсхолдеры `picsum.photos` с фиксированным seed на объект; реальные фото загружаются через админку;
- сид идемпотентен: повторный запуск не дублирует данные (проверено).

## 11. Следующий шаг

Схема, миграция и данные готовы. Дальше — service layer: репозитории, доменные сервисы каталога и заявок, локализующий маппер. Именно он обязан реализовать два правила, зафиксированных проверками: пересчёт `priceFromAmount` при правке юнитов и блокировку родителя при смене обложки (раздел 7.5).
