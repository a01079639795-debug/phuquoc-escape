02Как проверить самостоятельно

Не полагайся на отчёт — проверки воспроизводимы. Docker и установленный PostgreSQL не нужны: серверы поднимаются из npm-пакетов.

Все 46 проверок: схема, гонка при смене обложки, сид
npm run db:verify:all
Инварианты схемы отдельно — 16 проверок, Postgres в WASM
npm run db:verify
Гонка при смене обложки — настоящий Postgres, параллельные соединения
npm run db:verify:race
Сид на настоящей базе с проверкой объёмов и инвариантов
npm run db:verify:seed
Прогон на своей базе (нужен Docker)
docker compose up -d && npm run db:deploy && npm run db:seed

06Правила удаления — это бизнес-решения

Самая содержательная часть для ревью: onDelete определяет, что происходит с данными при удалении связанной записи.

СвязьПравилоПочему именно так
Request → Listing / ListingUnit / User SET NULL Заявка не должна исчезать вместе с объектом или аккаунтом — это лид, источник данных для будущей CRM и предмет возможного спора
Listing → Area RESTRICT Нельзя удалить район, в котором есть объекты. Скрытие района — через isActive, а не удалением
ListingImage → MediaAsset RESTRICT Нельзя удалить файл, пока он где-то используется
RequestNote → User (автор) RESTRICT Автор комментария не удаляется. Менеджеры блокируются (status = BLOCKED), а не стираются
Переводы, юниты, связи с удобствами, изображения, HotelDetails, BikeDetails → Listing CASCADE Части объекта не имеют смысла без него. При этом сам файл в MediaAsset остаётся
Session, UserToken, Favorite → User CASCADE —
Listing → User (owner), AuditLog → User (actor), MediaAsset → User SET NULL Объект и журнал переживают удаление аккаунта

07Принятые решения

Семь мест, где выбор был неочевиден. Все подтверждены 25.08.2026 и зафиксированы в схеме.

7.1Деньги — BigInt, а не Int

Int кончается на 2 147 483 647 VND (≈ 85 000 $). Для цены за ночь достаточно, для сумм броней и будущего ledger — нет, а менять тип колонки на живых данных означает перезапись таблицы и правку всех типов в коде.

Цена решения: BigInt не сериализуется в JSON штатно. Форматирование денег обязано идти через маппер service layer — он и так предусмотрен архитектурой.

7.2timestamptz вместо timestamp

Prisma по умолчанию генерирует TIMESTAMP(3) без таймзоны. Проставил @db.Timestamptz(3) всем 28 полям времени. Без этого прямой SQL, BI-инструменты и будущий вынос API в NestJS могут прочитать время неверно. Даты аренды при этом остались DATE — ночь это календарный день, а не момент времени.

7.3uuid(7) генерируется Prisma Client, а не базой

У колонок нет DEFAULT gen_random_uuid().

Плюс: версия 7 упорядочена по времени — хорошая локальность индекса и естественная сортировка. Минус: вставки чистым SQL обязаны передавать id явно. В сиде это учтено.

7.4slug канонический, один на все языкиподтверждено

URL будут /ru/hotels/villa-sunrise и /en/hotels/villa-sunrise — один слаг, разный контент. Отдельные слаги по языкам добавляются позже полем в ListingTranslation с фолбэком в резолвере.

7.5Единственность обложки держит service layer — с обязательным условием

Prisma не поддерживает частичные unique-индексы (WHERE isCover = true), а сырой SQL в миграции ломает prisma migrate dev — расхождение схемы и теневой базы. Решение оставлено за service layer.

Тест на конкурентное обновление показал, что очевидная реализация ломается. Наивная последовательность «снять флаг со всех → поставить нужному» под параллельной нагрузкой оставляет две обложки. Механика гонки в PostgreSQL при READ COMMITTED:

T1: UPDATE … SET isCover=false WHERE listingId=X AND isCover=true   → блокирует строку A
T2: UPDATE … SET isCover=false WHERE listingId=X AND isCover=true   → ждёт на строке A
T1: UPDATE … SET isCover=true  WHERE id=B
T1: COMMIT
T2: разблокирован. Строка A уже false и под условие не подходит.
    Строку B он не видит: на старте его UPDATE она была false.
    В итоге T2 не снимает ничего.
T2: UPDATE … SET isCover=true  WHERE id=C
T2: COMMIT
                                    → обложки B и C. Инвариант нарушен.

Обязательный рецепт: транзакция смены обложки начинается с блокировки родительской строки.

BEGIN;
SELECT id FROM "Listing" WHERE id = $1 FOR UPDATE;   -- сериализует смену
UPDATE "ListingImage" SET "isCover"=false WHERE "listingId"=$1 AND "isCover"=true;
UPDATE "ListingImage" SET "isCover"=true  WHERE id=$2;
COMMIT;

Проверено: с блокировкой два параллельных запроса дают одну обложку, десять одновременных — тоже одну. Тест зафиксирован в репозитории (npm run db:verify:race), чтобы регрессия в service layer была поймана. Тот же приём — основа защиты от двойного бронирования на этапе 2: механизм отрабатывается заранее на безопасном поле.

7.6ListingImage.alt — единственный переводимый текст вне translation-таблицы

Пятая таблица переводов ради alt-текста показалась несоразмерной. Заполняется на языке контента.

7.7Amenity.group — строковый код, а не отдельная таблица

Группы удобств («internet», «food», «equipment») нужны только для группировки в админке. Подписи живут в словарях интерфейса.

09Чего в схеме сознательно нет

Booking, UnitAvailabilityDay, RatePlan, Payment, Client, Deal, отзывы.

Это не упущение: пустые неиспользуемые таблицы усложняют схему и всё равно будут спроектированы точнее, когда дойдём до задачи. Текущая модель им не мешает — см. раздел 8.

Особенности реализации

  • контент только на RU — как договорились; добавление EN и VI является вставкой строк в *Translation;
  • priceFromAmount считается как минимум по активным юнитам — тем же правилом, которое затем реализует service layer;
  • пароль всех демо-аккаунтов demo1234, хэш настоящий argon2id — аккаунты заработают сразу, как появится авторизация;
  • изображения — стабильные плейсхолдеры picsum.photos с фиксированным seed на объект; реальные фото загружаются через админку;
  • сид идемпотентен: повторный запуск не дублирует данные (проверено).

11Следующий шаг

Схема, миграция и данные готовы. Дальше — service layer: репозитории, доменные сервисы каталога и заявок, локализующий маппер.

Именно он обязан реализовать два правила, зафиксированных проверками: пересчёт priceFromAmount при правке юнитов и блокировку родителя при смене обложки (раздел 7.5).
