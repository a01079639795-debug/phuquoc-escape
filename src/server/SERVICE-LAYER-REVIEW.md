## 1. Что сделано

Слой бизнес-логики поверх утверждённой схемы: 22 файла, 3288 строк кода и 699 строк тестов.

Слой не зависит ни от Next.js, ни от HTTP. Это и есть то, ради чего он выделен: когда на этапе 2–3 понадобится вынести API и фоновые процессы в отдельный сервис, переносится каталог `src/server` целиком, а бизнес-логика не переписывается.

**Не создавалось по договорённости:** UI, транспортный слой, `Booking`, `Payment`, CRM, адаптер объектного хранилища.

## 2. Две ошибки, найденные в процессе

Обе — мои собственные, обе исправлены и закрыты проверками.

### 2.1. Депозиты в USD были записаны в долларах, а не в центах

Соглашение, принятое вместе со схемой: деньги хранятся целыми числами в **минорных** единицах. Для VND минорная единица совпадает с основной, а для USD это цент. В сиде депозиты за байки были записаны как `150`, что означает залог **$1.50**, а не $150.

Ошибка проявилась бы не сразу: цены в VND корректны, и каталог выглядел бы правильно. Разошлось бы только на этапе оплат, когда депозит начал бы реально списываться.

Исправлено (`150 → 15000` и далее). В проверку сида добавлен барьер: депозит в USD меньше `1000` центов считается признаком повторения этой ошибки.

### 2.2. Honeypot-поле было мёртвым кодом

Приманка для ботов объявлялась в схеме как `website: z.string().max(0)`. Из-за этого zod отбраковывал поле **раньше**, чем срабатывала проверка в теле сервиса: код антибота никогда не выполнялся, а бот получал подробное сообщение об ошибке именно по скрытому полю — то есть система сама подсказывала, на чём он попался.

Тест это поймал. Схема теперь принимает поле, а решение принимает сервис.

Починка вскрыла более общую проблему: наружу летел `ZodError`. Это означало, что транспортный слой обязан знать про библиотеку валидации, и при выносе API в NestJS такой код пришлось бы переписывать. Добавлен `parseInput`, все **21** точка валидации переведены на него — теперь наружу выходит только доменная `ValidationError` с разбором по полям.

## 3. Структура

```
src/server/
├─ index.ts              единственная точка входа для транспорта
├─ db.ts                 PrismaClient (singleton, защита от утечки соединений в dev)

├─ lib/
│  ├─ locale.ts          единый слой мультиязычности с цепочкой фолбэков
│  ├─ money.ts           BigInt ↔ DTO, минорные единицы, форматирование
│  ├─ crypto.ts          argon2id, хэши токенов
│  ├─ text.ts            slug с транслитерацией, E.164, publicCode
│  ├─ validate.ts        zod → ValidationError
│  ├─ audit.ts           журнал в той же транзакции, что и изменение
│  ├─ idempotency.ts     защита от двойной отправки формы
│  └─ rate-limit.ts      счётчики попыток
│
└─ modules/
   ├─ auth.service.ts          ├─ favorites.service.ts
   ├─ users.service.ts         ├─ media.service.ts
   ├─ catalog.service.ts       ├─ dictionaries.service.ts
   ├─ listings.service.ts      └─ admin.service.ts
   └─ requests.service.ts
```

`src/server` — граница, которую клиентский код не пересекает. Она проходит по каталогу, а не по соглашению об именах файлов.

## 5. Правила, вынесенные из вызывающего кода в сервисы

Три вещи, которые нельзя было оставить на усмотрение того, кто вызывает.

### 5.1. Смена обложки — только под блокировкой родителя

Правило из решения 7.5 предыдущего этапа, доказанное race-тестом. Реализовано в `listings.service.ts`:

```ts
await prisma.$transaction(async (tx) => {
  await lockListing(tx, listingId);   // SELECT … FOR UPDATE — не убирать
  …
});
```

Тот же приём (`SELECT … FOR UPDATE` по родителю) станет основой защиты от двойного бронирования на этапе 2. Механизм отрабатывается заранее на безопасном поле.

### 5.2. Пересчёт цены «от»

`priceFromAmount` — денормализация ради сортировки и списков без JOIN. Её актуальность обеспечивает `recomputePriceFrom`, вызываемый при любом изменении юнитов: добавление, правка, деактивация, удаление.

### 5.3. Владение проверяется запросом, а не сравнением

```ts
prisma.request.findFirst({ where: { id: requestId, userId: actor.id } })
```

Не «выбрать, потом сравнить». Это единственная надёжная защита от IDOR при росте числа эндпоинтов, и она закрыта отдельным тестом.

## 6. Мультиязычность

Договорённость: схема поддерживает RU, EN и VI, контент MVP заполняется только на RU.

Чтобы добавление языка позже осталось вставкой строк, а не правкой бизнес-логики, **все** чтения переводимого текста идут через `lib/locale.ts`. Ни один сервис не обращается к `translations[0]` напрямую.

Цепочка фолбэков задана для каждого языка, поэтому страница не окажется пустой из-за отсутствия перевода:

| Запрошен | Порядок подбора |
|---|---|
| RU | RU → EN → VI |
| EN | EN → RU → VI |
| VI | VI → EN → RU |

## 7. Безопасность

Что из списка рисков архитектуры закрыто на уровне сервисов.

| Риск | Реализация |
|---|---|
| **IDOR** | владение проверяется в запросе; guard на роль отдельно; закрыто тестом на чужую заявку |
| **Перебор пароля** | argon2id, ограничение частоты по IP и по адресу, сброс счётчика при удачном входе |
| **Enumeration** | одинаковый ответ для несуществующего адреса и неверного пароля; запрос сброса не раскрывает наличие аккаунта |
| **Кража сессии** | в базе только sha256 токена; отзыв мгновенный; смена пароля обрывает остальные сессии; блокировка действует немедленно |
| **Спам в форме** | ограничение частоты по IP и телефону, honeypot, идемпотентность |
| **Загрузка файлов** | SVG запрещён, потолок размера, ключ генерирует только сервер |
| **DoS на поиске** | жёсткий потолок `perPage`, который нельзя обойти параметром |
| **Утечка PII** | контакты заявки отдаются только в админском DTO; пользовательский DTO их не содержит |

Ограничение частоты держит счётчики в памяти процесса. Для монолита MVP на одном инстансе этого достаточно; при нескольких инстансах счётчики надо переносить в Redis. Сигнатура `consume` при этом не меняется, вызывающий код останется прежним. Ограничение записано в комментарии модуля.

## 9. Как запустить

Без Docker — поднимет свой сервер, применит миграцию, выполнит сид и проверит результат:

```bash
npm run db:verify:seed
```

На своей базе:

```bash
docker compose up -d && npm run db:deploy && npm run db:seed
```

Тесты сервисов:

```bash
npm test
```

Пароль всех демо-аккаунтов — `demo1234`. Администратор: `admin@phuquoc.demo`.

Сид идемпотентен: чистит данные в порядке, учитывающем RESTRICT-связи, и наполняет заново. Повторный запуск проверен отдельным утверждением.

## 10. Известные ограничения

Названы явно, чтобы не выглядели упущением.

| Ограничение | Когда снимается |
|---|---|
| Счётчики частоты в памяти процесса — обнуляются при перезапуске и не общие для нескольких инстансов | при переходе на несколько инстансов, переносом в Redis |
| Presigned-загрузка и проверка magic bytes отсутствуют — есть только учёт файлов и политика допустимости | вместе с адаптером R2/MinIO |
| Уведомления о новой заявке не отправляются | следующий шаг, пункт 2 ниже |
| Нормализация телефона упрощённая: цифры с ведущим плюсом, без разбора планов нумерации | при подключении libphonenumber, если понадобится точность |
| `npm run verify:all` последовательно поднимает четыре сервера и потому долгий | при желании — параллелизация или общий сервер на все наборы |

## 11. Рекомендуемые следующие шаги

1. **Транспортный слой** — route handlers Next.js поверх сервисов: разбор cookie сессии, маппинг `AppError.status` в HTTP, CSRF-токен. Тонкий слой без бизнес-логики.
2. **Уведомления** — Telegram и почта на новую заявку. Сейчас заявка создаётся, но менеджер о ней не узнаёт: это разрыв в главном сценарии конверсии MVP.
3. **Адаптер хранилища** — R2/MinIO, presign и проверка magic bytes при подтверждении загрузки. До этого админка не сможет загружать реальные фотографии.
4. **UI** — после того, как транспорт зафиксирован.

Порядок именно такой: пункты 2 и 3 закрывают функциональные дыры, из-за которых демо не отработает целиком, а UI поверх готового транспорта делается быстрее и без переделок.
