02Два найденных дефекта

Оба — мои собственные, оба исправлены и закрыты тестами.

2.1 Коды ошибок собирались из русских названий исправлено

NotFoundError строил код как ${entity.toUpperCase()}_NOT_FOUND, где entity — человекочитаемое название. Наружу уходило ОБЪЕКТ_NOT_FOUND.

Код ошибки — машинный идентификатор: по нему клиент ветвит поведение, по нему группируются логи. Кириллица делает его непригодным, и вдобавок он менялся бы при первой правке формулировки.

const ENTITIES = {
  listing: { code: 'LISTING', message: 'Объект не найден' },
  request: { code: 'REQUEST', message: 'Заявка не найдена' },
  …
} as const;

Заменено типизированным справочником: код и текст разделены, ключи проверяет компилятор. Дефект нашли тесты транспорта — на уровне сервисов он не был виден, потому что там ошибку ловят по классу, а не по коду.

2.2 Снятие EXIF ломало разбор размеров исправлено

Первая реализация вырезала из JPEG все блоки APPn. Файл остаётся формально валидным, но без заголовка JFIF строгие анализаторы перестают читать размеры.

Интеграционный тест этого не поймал: размеры снимаются с исходных байтов до очистки. Поймал модульный тест на самой функции.

Теперь вырезаются APP1 (EXIF с геометкой и XMP), APP3–APP15 и комментарии. APP0 (JFIF) и APP2 (цветовой профиль ICC) сохраняются: первый структурный, второй отвечает за цветопередачу. Если APP-заголовка не осталось — подставляется минимальный JFIF.

03Транспорт: обработчики остаются тонкими

Типичный обработчик 3–8 строк, самый длинный 21. Целиком:

import { handle } from '@/server/http/handler';
import { catalog } from '@/server';

export const GET = handle<{ slug: string }>(async (ctx) =>
  catalog.getListingBySlug(ctx.params.slug, ctx.locale),
);

Всё общее живёт в обёртке handle(): разбор cookie сессии, проверка CSRF, разбор параметров пути и строки запроса, единый конверт ответа, перевод доменных ошибок.

Обработчики генерируются из таблицы в scripts/generate-routes.mjs. Причина не в экономии: сорок с лишним почти одинаковых файлов невозможно проверить глазами на предмет просочившейся логики, а одну таблицу — можно.

Разбор строки запроса

Повторяющиеся ключи собираются в массив (?amenities=pool&amenities=spa), true/false приводятся к булеву типу. Числа транспорт не трогает — их приводят схемы сервисов через z.coerce, поэтому одно и то же поле одинаково работает и в строке запроса, и в JSON-теле.

04Сессия и CSRF

CookieФлагиЗачем
pq_sessionHttpOnly, SameSite=Lax, Secure в продеТокен недоступен скриптам: XSS не даёт его украсть
pq_csrfбез HttpOnlyКлиент обязан прочитать и вернуть заголовком — в этом суть double submit

Токен сессии не попадает в тело ответа: он живёт только в cookie.

Проверка применяется к изменяющим запросам от аутентифицированного пользователя. CSRF эксплуатирует попутные полномочия — cookie, которую браузер отправляет автоматически. Без сессии подделывать нечего, а у гостя ещё нет токена, который можно было бы вернуть.

ЗапросПроверка
GET с сессиейне требуется
PATCH /me с сессиейобязательна
POST /requests от гостяне требуется — попутных полномочий нет
POST /auth/loginне требуется — сессии ещё нет

Для гостевых POST основной защитой остаётся SameSite=Lax.

06Хранилище

StoragePort и три реализации: S3Storage (R2 в проде, MinIO локально — протокол один), MemoryStorage для тестов, выбор по переменным окружения.

В продакшене без настроек приложение падает при старте; вне продакшена — предупреждение и память. Молчаливый переход на заглушку был бы хуже явного отказа.

Поток загрузки

1. Админка просит ссылку
     POST /admin/media/upload-url  { mime, sizeBytes }
       └─ сервер проверяет тип и размер, генерирует ключ (UUID),
          возвращает presigned PUT

2. Браузер кладёт файл НАПРЯМУЮ в R2 или MinIO
     (через наш сервер файл не идёт: нет нагрузки и нет лимитов body-parser)

3. Админка подтверждает
     POST /admin/media/confirm  { storageKey }
       └─ и вот здесь мы впервые видим содержимое

Что проверяется при подтверждении

ПроверкаПоведение

Заявленный тип ≠ фактическийВ базу пишется фактический

Ключ объекта генерирует только сервер: имя файла от клиента открыло бы путь к перезаписи чужих объектов и path traversal.

07Уведомления

NotifierPort и три реализации: TelegramNotifier (Bot API через fetch), ConsoleNotifier (без настроек пишет в лог вместо отправки), MemoryNotifier для тестов.

Два правила

  • сбой канала не роняет заявку — она уже сохранена, и недоступный Telegram не повод отвечать клиенту ошибкой;
  • отправка не блокирует ответ — уходит в фон.

Из-за второго правила добавлен flushNotifications(): иначе фоновую отправку невозможно проверить детерминированно.

Повтор с тем же ключом идемпотентности до отправки не доходит — дубля сообщения менеджеру не будет.

Электронная почта не реализована по указанию. Добавляется новой реализацией того же интерфейса.

О персональных данных

Сообщение содержит контакты клиента — это рабочий инструмент: менеджер перезванивает, не открывая админку. Обратная сторона — персональные данные уходят во внешний сервис, поэтому чат обязан быть закрытым, а состав участников контролируемым. Отмечено в .env.example рядом с переменными.

Пользовательский текст экранируется: <script> в комментарии к заявке не станет разметкой.

10Рекомендуемые следующие шаги

  1. UI — публичный каталог, кабинет и админка поверх готового API. Транспорт зафиксирован, переделок не потребует.
  2. Электронная почта — подтверждение заявки клиенту и письма сброса пароля. Сейчас токен сброса возвращается сервисом, но отправлять его некому.
  3. MinIO в docker-compose — чтобы загрузка работала локально из коробки, без внешнего аккаунта.
  4. Развёртывание демо — Vercel, управляемый Postgres, R2.

Первым пунктом идёт UI: остальное — инфраструктура, которую удобнее настраивать, когда есть что показывать.
